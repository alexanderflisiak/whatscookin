## 2024-05-18 - [Critical SSRF vulnerability via Scraping Endpoint]
**Vulnerability:** The `/api/scrape` route allowed fetching any user-provided URL unconditionally, creating an SSRF (Server-Side Request Forgery) window into the backend network infrastructure. Furthermore, any resultant unhandled fetch exceptions were leaked directly to the client via `error.message`.
**Learning:** In Next.js App Router applications, unauthenticated proxy or scraping endpoints require stringent validation. By default, standard fetch will happily request `http://localhost:3000` or `169.254.169.254` (cloud metadata).
**Prevention:** Always implement an explicit hostname blocklist (private IP ranges, `localhost`, etc.) and ensure the protocol is restricted strictly to `http` or `https`. When proxying outbound requests, do not echo back raw trace/network errors to client API consumers.

## 2024-05-19 - [Critical SSRF IPv6 Bypass via Scraping Endpoint]
**Vulnerability:** The `/api/scrape` route implemented SSRF protection via a hostname blocklist in `isUrlSafe`, but only accounted for IPv4 addresses (`10.x.x.x`, `192.168.x.x`, `127.x.x.x`, etc.) and `localhost`. It completely omitted IPv6 addresses, meaning a user could bypass the protection by submitting an IPv6 loopback (`[::1]`) or private range URL, regaining internal network access.
**Learning:** Network protection blocklists must be comprehensive across both IP protocols. When blocking `localhost` and private IPv4 ranges, their IPv6 equivalents (like `::1`, `fc00::/7`, `fe80::/10`) must also be explicitly blocked to prevent straightforward bypasses.
**Prevention:** Always include IPv6 equivalents (`[::1]`, `[fc00:`, `[fe80:`) when implementing manual IP-based blocklists for SSRF protection, or preferably use a robust networking library designed to resolve and filter out all internal/private IPs uniformly before connection.
