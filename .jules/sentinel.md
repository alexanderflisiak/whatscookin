## 2024-05-18 - [Critical SSRF vulnerability via Scraping Endpoint]
**Vulnerability:** The `/api/scrape` route allowed fetching any user-provided URL unconditionally, creating an SSRF (Server-Side Request Forgery) window into the backend network infrastructure. Furthermore, any resultant unhandled fetch exceptions were leaked directly to the client via `error.message`.
**Learning:** In Next.js App Router applications, unauthenticated proxy or scraping endpoints require stringent validation. By default, standard fetch will happily request `http://localhost:3000` or `169.254.169.254` (cloud metadata).
**Prevention:** Always implement an explicit hostname blocklist (private IP ranges, `localhost`, etc.) and ensure the protocol is restricted strictly to `http` or `https`. When proxying outbound requests, do not echo back raw trace/network errors to client API consumers.

## 2026-04-07 - Prevent SSRF via IPv6 normalization & HTTP Redirects
**Vulnerability:** The scraper endpoint (`/api/scrape`) had a partial SSRF blocklist that could be bypassed using IPv4-mapped IPv6 addresses (which Node's `URL` normalizes to hex, e.g., `[::ffff:127.0.0.1]` -> `::ffff:7f00:1`), unique local IPv6 addresses, and by chaining redirects since `fetch` implicitly follows them.
**Learning:** Node.js URL parses IPv6 hosts with brackets intact, meaning a regex strictly checking `127.` fails to match `[::ffff:127.0.0.1]`. Furthermore, URL normalizes mapped IPv4 representations so standard decimal checks fail. Default `fetch` behavior blindly follows redirects to any destination, nullifying pre-fetch URL validation.
**Prevention:** Always strip brackets from IPv6 hostnames before validation. Be aware of underlying URL parser normalization rules (like hex conversions) when creating blocklists. Validate URLs on *every* redirect using `redirect: 'manual'` rather than just validating the initial user-provided URL.
